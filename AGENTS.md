## Layout and checks

Two Go modules in one workspace (`go.work`): `memory/` is the harness-neutral engine (public packages, no
harness SDK; `memory/hostinfo` and `tokens.EstimateMessageTokens` are what an adapter injects), and
`extensions/observational-memory/` is the PiG adapter (SDK `github.com/MichaelKinsy/PiG/extensions/sdk`), which
requires the core through a local `replace` that PiG promotes into its build; PiG hashes every workspace member, so
a core change rebuilds the extension. The memory model is shared with the TypeScript Pi extension
elpapi42/pi-observational-memory; `docs/pig.md` lists where it deliberately differs. `sdk.New(Name)` must equal the
factory directory name, so do not rename that directory or `Name` independently. Only the adapter's
`internal/sdkhost` (and its root `hostinfo.go`) touch the SDK; the engine runs against `memory/host` interfaces, and
tests use the fakes in `memory/testfix`. Memory v2 (`docs/memory-v2.md`) is the only engine: memory v1's background
workers, scheduling, catch-up, moved cut and worker models are deleted, but the data v1 wrote (records, `om.folded`
compactions with `foldThroughEntryId`, coverage markers, layer files, held definitions, rules, the curated store) must
keep loading. Check each module: `cd memory` (and `cd extensions/observational-memory`) `&& gofmt -l . && go vet ./...
&& go test -race ./...` (CI runs both; under a tight memory limit add `-p 2`); registrations: `pig install
./extensions/observational-memory --validate-only --json`. The code tool's `memory/om/docs_gen.go` and
`memory/sandbox/symbols` are generated (`cd memory && go generate ./om ./sandbox`, run as tests with `-write`);
their tests fail on a diff or an undocumented om export. The language-neutral contracts (`contracts/README.md`,
`docs/protocol.md`) are checked by `memory/contracts`: every stored file and entry must validate against
`contracts/schemas` (a new stored shape needs a schema), and `contracts/golden` is generated (`go test ./contracts
-args -write`) and compared byte for byte, so a change to level 0 or the summary regenerates it. Keep `main` packages out of the PiG adapter module (PiG
refuses one there); the `om` binary for other harnesses is `memory/cmd/om` (`memory/cli`, `docs/universal.md`):
it runs the engine over `memory/neutral` (the engine's entries in `~/.om` beside a transcript `memory/transcript` reads,
never writing the harness's files) and makes no model request; its harness registry is data only (`memory/cli/assets/harnesses.json`, schema `contracts/schemas/registry.schema.json`, vocabulary in `docs/universal.md`; a harness is one entry, code only for a new named resolver, mapper or install kind, and `docs/harnesses.md` is generated from it with `go test ./cli -run HarnessDoc -args -write`); `memory/engine` is the session setup both adapters share. Building the PiG checkout itself needs `GOFLAGS` unset (it is a Go workspace).
`lisp/` is the SBCL memory core being ported from the Go engine, one image per user with each model's memory live in it (`docs/lisp-core.md` is the design and the port plan; `docs/lisp-spike.md` the first slice, `docs/lisp-port-*.md` each work package's state), built on the SBCL pinned in `lisp/SBCL_VERSION` (`docs/lisp-build.md`; CI's `lisp` job runs both checks on it and uploads the image, a local SBCL only warns): `sbcl --non-interactive
--load lisp/run-tests.lisp`, and `cd memory && OM_LISP_PARITY=1 go test -count=1 -p 1 ./selection ./transcript ./contracts ./cli ./enginerpc -run Lisp`
diffs it against Go byte for byte (summaries, readers and store, curated and `SettleV2`, the image end to end; skipped
without the variable or `sbcl`). Lisp packages load in `lisp/om-engine.asd` order: a file added to `om.base`/`om.kernel`/
`om.engine` loads before that group's `end-*` file. The image is the default engine of `om` and the PiG adapter (`lispimage.Select`, `config.ReadEngine`; `OM_ENGINE=go` or `"engine": "go"` is the kill switch, Windows stays on Go), built on first use from the embedded copy `memory/lispimage/sources` (regenerate it with `cd memory && go test ./lispimage -run Sources -args -write` after a change under `lisp/src`; `docs/lisp-build.md`); Go test packages that run om or the adapter set `OM_ENGINE=go` in `TestMain`, so no suite depends on sbcl.

## The memory tool, curated memory and the harness

The extension registers one tool, `memory`, which runs Go code (`docs/code-tool.md`; surface in `memory/omtool`,
fixed text identical for every model, never re-registered): `harness.Manager.RunMemory` checks it with
`memory/codepolicy`, runs it in the namespace child (`memory/sandbox`, one per process, killed at
`session_start`/`session_shutdown`), answers `om` calls with `memory/omhost` over a branch snapshot, keeps compiled
declarations in `memory/codestore` (provenance via `memory/provenance`), and records one `ModelKindCode` event
from `omtool.Details`, which level 0 (`writes`) and `dropped-then-queried` (`recalled`, `searches`) read back. A search no row matches with
every word ranks the rows by matched words instead (`Partial`, `om.PartialNotice`, paged by `Limit`), never in a
detector's reads. Old
query text is never run: `memory/legacyquery` (frozen) answers it with a snippet hint and still reads old calls,
stored definitions and `ledger.LegacyTablesRecallParagraph` summaries. Every printed pointer is an om snippet from
`om.FormatRead` (no comma, quote or `|`, so it survives every codec); tests run them through a real child with
`memory/snippettest`. Fixed texts name snippet forms through `om.Snippet*`, whose values are the placeholders
`om.IsPlaceholder` lists (``om.Recall(`<id>`)``), refused if run as they stand; never print a bare-letter example. A child kill goes through `harness.Namespace.kill`, which re-reads the store's types and digests for the next call's policy check, and `forget` refuses a name its own call declares. The root `lifecycle_test.go` drives events and tool calls through the registered extension over a pipe with `PIG_HOME` set to a temp dir (a root test that reaches the real host must never write `~/.pig`). The query language's interpreter is deleted; `memory/legacyquery` only reads old text. Defined tools are retired: `harness.Manager.SkipNames` keeps their names, `om.Retired()` and `/om:status` list them; never register, run or grade one. Slash commands stay read-only views
(`/om:status`, `/om:view`); `/om:status` reads the code store and the supervisor's record, never starting a child.
`memory/curated` is the agent-written memory (store under PiG's config root, retired defined queries loaded and listed only, ranked index, staging
and `curated.Check` on every write and load, forget retires); writes go through `curated.Call.Run`.
`memory/harness` is the per-model harness: profiles are a pure function of
`<store>/models/<model>.jsonl` (`harness.Compute`, `MinEvidence`) over the events tagged `engine: v2` only, one unit
per compaction; it owns the memory tool's execution and registers no other tool. `om.Propose` is refused (`omhost.ErrDefinedInLevel1`); `om.LayerForget` and `om.LayerRollback` act on the session
model's layer and never touch rules (`rules.IsRule`). Definitions and
rules are proposed only inside the level-1 request (`hooks/definitions_v2.go`, `rules.CheckV2Definition`), pass
`harness.CheckModelDefinition`, are held and settled only by `rules.SettleV2` on later compactions' evidence.
`memory/rules` decides only rules tagged `engine: v2` (v2 detectors: a kernel check, or a model's Go `func Count() int` that passes `codepolicy.CheckDetector`, run in its own child after each compaction by `hooks/detectors_v2.go`, never inside the hook, killed at the next compaction, `session_start` or `session_shutdown`; code remedies `keep-head`, `switch-codec`;
`long-spec` is retired and listed, never applied); v1's rules and remedy names still parse (`rules.Check`, `ProtectKindMaxFullness`) and are listed,
never applied. `memory/kernel` is what no definition may touch (`kernel.Owns`, `Check`, the floor,
`kernel-consolidate`; v1's retired prompt ids stay owned); `memory/layer` stores the model-built definitions and
re-runs `kernel.Check` on every load; `curated.Store.Layer` always applies only v2's holds, so a definition v1
held never runs; v1 worker instructions are only folded by `layer.Store.MigrateToV2` at session start. Keep `kernel`
a leaf (its tests check its lists against the defining packages), and never hold the curated store's lock when
calling a layer method that takes it (use the `*Locked` variants). The index goes into the system prompt as the
`curated-memory` section (`systemPromptOptions.sections`), never as a returned `systemPrompt`, which PiG turns into a
forced prompt that drops other extensions' sections. PiG keeps the extension process across sessions, so
per-conversation state (the index `Pin`) resets on `session_start`.

## Model auth (OAuth vs API key)

`memory/runtime/runtime.go` `resolveCandidate` must accept auth that carries EITHER an API key OR
non-empty headers (e.g. `Authorization: Bearer …`), or a provider the host reports as configured for
request-time signing. OAuth providers return headers-only auth from
`GetApiKeyAndHeaders`. The rule mirrors Pi's `AgentSession._getRequiredRequestAuth`
(`result.auth.apiKey || result.auth.headers`). Do not re-introduce a hard API-key requirement — it
breaks the level-1 request for every OAuth model. The level-1 request resolves the session model
alone (`Runtime.ResolveSessionModel`); there is no worker model and no fallback model.

- The request rule (`docs/memory-v2.md`): no model request outside a compaction and at most one inside it. Every request goes through `agents.Request` and logs one request event (`debuglog.IsRequest`); tests count them with `testfix.CountRequests`.
- Compaction, level 1 and memory storage use separate token domains: the trigger compares PiG's reported context with PiG's threshold (`hooks.ReadV2Threshold`), the summary budget comes from `tokensBefore` and the removed source (`config.ResolveV2SummaryBudget`, headroom only on the threshold bound), and pools, serialized input and stored memory use local estimates. Changes to token accounting must align the trigger, status, documentation, and tests. Pi exposes aggregate active-context usage, not per-entry attribution, so provider context cannot replace raw-entry counting.
- Pi context pressure and compactable history are separate conditions: `Host.Compact` can fail before `session_before_compact` when Pi finds no removable range. The only trigger (`hooks.maybeTriggerCompactionV2`) runs with PiG's auto-compaction off, at an idle `agent_settled`, when reported context > window - reserveTokens (`config.PiCompactionTokens.ReserveTokensFor`, read under trust), never with unknown usage; after "Nothing to compact" it is suspended until the branch tip changes (`runtime.CompactionBackoff.TipID`), since `firstKeptEntryId` is a retention boundary and retained source can stay above the threshold.
- `session_before_compact` (`hooks/compaction_v2.go`) always returns a compaction on PiG's exact cut, never nil or cancel; a panic anywhere in the handler (`extension.go` included) is recovered into `hooks.RecoveredCompactionV2`, the brief is bounded by the removed source tokens, and only the request's own context cancels it (`sdkhost.Host.RequestContext`, never `ctx.Signal()`).
- Compaction must never discard source no extraction read: level 0 (`memory/extract`, pure; `hooks/extract_v2.go`) runs at `turn_end` and, for the unextracted cut range, inside the hook before rendering. Records go in one `om.observations.recorded` batch per cut-point segment (a cut-point entry and its tool results), so a cut folds exactly the batches whose entries it removes, plus an `om.extracted` marker when the last batch stops short (`ledger.ExtractionProgressIndex`); appends are deduplicated against a fresh `GetBranch()` under `extractMu`. Coverage markers are positional claims: code that appends one must have read every source entry after the previous one. Tool results give `value` and `evidence` records (`extract/output.go`, `lisp/src/output.lisp`, docs/memory-v2.md "Tool output"): hand-written ASCII-class scanners, so a grammar change goes into both engines with a case in `selection/testdata/lispparity/tooloutput.jsonl`; record counts in fixtures (the Lisp trial's `expected.json`) move with them.
- The summary is `selection.Render` from the ledger, never summary-of-summary: ordered classes, no weights, every line ending with its anchor (`ledger.ObservationAnchor`), and everything left out printed as an om snippet that must list it (tests run it through `memory/snippettest`); its drops are `extract.Drops` over what it shows. `details` carry the full projection. Its `intent` (quoted requests, `hooks.v2Intent`) and `next` (`selection.markNext`) sections are code-built; their instruction lines are inserted only when shown (header cost), so read a summary's records with `ledger.TablesSummaryBody`, never by stripping `selection.TablesInstructions`.
- Thinning (`memory/thin`, the `context` event in `hooks/thin_v2.go`) edits messages in place and returns nil (a replaced list makes PiG collapse its system messages); its plan reads the branch only up to the latest compaction and is cached per compaction (`Runtime.CachedThinPlan`), so request bytes change only at a compaction. The same event first adds day headers (`thin.DayHeaders`), read from each message's own timestamp only, so they never change an earlier message's bytes.
- Level 1 (`hooks/consolidate_v2.go`, validation in `memory/consolidate`, fixed rules in `kernel.TextConsolidateRules`, `kernel-consolidate` first in the prompt) is one `agents.RunSingleRequest` on the session model, skipped with `consolidate: false`, passive, overflow, the extension's own compaction (`rt.CompactInFlight()`), a cancelled request context, or when it does not fit the window (`config.PiGContextSafetyTokens`). It accepts only ids the prompt showed, drops a record only when the one standing for it carries its specifics as whole items (`consolidate.dropsSpecifics`, never `ledger.MissingSpecifics`' substring match), appends nothing on any failure, and records its result in `details.consolidation`.
- One status rule: `ledger.MaySupersede` (a plan or condition never supersedes a fact; a retraction withdraws only a plan or condition) governs level 0's corrections and links and level 1's supersedes and confirms; level 1 never merges records with different statuses and settles only the `possibly_updates` pairs its prompt listed (`consolidate.Input.Links`). Level-1 records name what they replace (`Observation.Replaces`, legacy via `ledger/replace.go`), folded through `FoldedLedger.ReplacedBy` to `ledger.Standing`; only the point-in-time view (`asof`) uses `FoldLedgerUnresolved` + `ResolveFolded`, and plain `until`/`through` must keep filtering current memory because the summary's printed queries rely on it.
